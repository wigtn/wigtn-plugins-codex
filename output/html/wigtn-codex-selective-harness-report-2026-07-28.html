Executive conclusion

결론 먼저

WIGTN Plugin은 Codex보다 코드를 더 잘 쓰는 프롬프트 묶음이 아니다. PRD, 화면 명세, 구현 계획, 요구사항 검증, Git 릴리스처럼 반복되는 제품 개발 작업을 재사용 가능한 기능으로 만든 Plugin이다.

4/4 = 4/4 GPT‑5.6 Sol bug fix에서 Bare와 개정 전 Plugin의 공식 성공률은 같았다.
+141.2% 같은 성공에 개정 전 Plugin이 사용한 output token 중앙값 증가분이다.
0/3 → 3/3 GPT‑5.5에서 명시한 PRD 계약의 충족률은 Plugin 사용 시 높아졌다.
일반 코딩은 Codex의 기본 동작에 맡긴다. WIGTN Plugin은 PRD 형식, 요구사항 ID, 수용 근거, 중단 재개 상태, Git 권한처럼 모델이 스스로 알 수 없는 제품 개발 규칙을 맡는다.

0.3.0에서는 구현을 지휘하는 절차를 줄이고 Specification, Planning, Verification, Release의 네 경계에 기능을 집중했다.

이 보고서는 일반 코드 품질 향상을 주장하지 않는다. 어디에서 Plugin이 도움이 됐고, 어디에서는 비용이 됐는지 측정한 뒤 제품 설계를 고친 과정을 보고한다.

01 · Product origin

왜 WIGTN Plugin을 만들었나

반복되는 제품 개발 요청을 기능으로 묶었다

Codex를 사용하다 보면 “아이디어를 PRD로 정리해줘”, “화면 명세와 구현 계획으로 바꿔줘”, “요구사항이 코드에 반영됐는지 확인해줘”, “변경 범위를 검토하고 커밋해줘” 같은 요청이 반복된다.

매번 긴 프롬프트로 작업 순서와 출력 형식을 설명하는 대신, WIGTN Plugin에 담을 제품 개발 규칙을 호출 가능한 Codex skill로 묶는 것이 출발점이었다. 목표는 코딩 방식을 통제하는 것이 아니라 반복 작업의 입력, 산출물, 완료 조건을 일정하게 만드는 것이었다.

Claude 플러그인을 복사하지 않고 Codex용으로 다시 설계했다

기존 Claude Code 플러그인의 역할 agent, slash command, 고정 오케스트레이션은 Codex의 skill 선택 방식과 기본 구현 루프에 그대로 맞지 않는다. 같은 역할을 중복하거나 일반 코딩 요청까지 무거워질 수 있었다. Claude 플러그인은 수정하지 않고 Codex용 구현을 별도 저장소에 만들었다.

02 · Research question

왜 모델 성능까지 측정했나

유용한 산출물을 만드는 Plugin이 구현 과정에도 항상 도움이 되는 것은 아니다. skill 설명, 계획 단계, 별도 검사, evidence 표는 모델의 탐색과 종료 판단을 바꾼다. 성공률이 그대로인데 명령과 token만 늘 수도 있다.

연구 질문측정값
RQ1. 일반 코딩을 방해하는가Plugin이 Bare 성공을 실패로 바꾼 pair
RQ2. 코드 결과를 개선하는가Bare 실패 / Plugin 성공 pair
RQ3. 제품 계약을 더 잘 지키는가PRD·acceptance contract 충족률
RQ4. 같은 결과에 비용이 얼마나 드는가wall time, output token, command

GPT‑5.5+Plugin과 GPT‑5.6 Bare를 직접 비교하지 않았다. 각 모델 안에서 같은 task와 실행 조건을 사용하고 Plugin만 켜고 껐다.

03 · Method

평가 방법

서로 다른 결과를 하나의 점수로 합치지 않았다

평가층확인한 것자료
계약 회귀manifest, trigger, schema, authority저장소 정적 검사
산출물 행동PRD·acceptance 형식 준수GPT‑5.5/5.6 smoke, ablation
실제 bug fix같은 코드 과제의 성공률과 비용SWE-bench Verified
어려운 featureceiling을 낮춘 positive liftFeatureBench pilot

외부 과제 포함 기준

  1. 문제문과 base commit이 고정되어 있다.
  2. clean base에서 핵심 test가 실패한다.
  3. gold patch가 같은 evaluator를 통과한다.
  4. fail-to-pass test가 문제문에 적힌 동작을 검사한다.
  5. pass-to-pass test가 기존 동작의 회귀를 검사한다.
  6. 격리된 환경에서 재현된다.
  7. agent가 hidden test와 reference patch를 볼 수 없다.

주효과 평가 설정

모델gpt-5.6-sol, reasoning high
Codex CLI0.145.0
Benchmarkprinceton-nlp/SWE-bench_Verified
과제astropy__astropy-12907, pytest-dev__pytest-10051
반복과제당 2회, Bare→Plugin / Plugin→Bare 순서 교차
환경공식 per-instance Docker, 매 trial clean workspace
판정official resolved, pass-to-pass, wall time, output token, command

분석 단위는 task × repetition의 paired block 네 개다. 표본이 작고 discordant pair가 없어 통계적 유의성을 주장하지 않는다.

05 · Design changes

실험 뒤 무엇을 바꿨나

구현 경로를 Fast와 Assurance로 나눴다

경로사용하는 경우실행 범위
Fast국소 변경, 낮은 위험, 저장소 테스트 실행 가능inspect → minimal patch → focused test → 관련 suite 1개
Assuranceauth, schema, persistence, concurrency, migration, 복수 요구사항stable ID, invariant, provenance, evidence artifact

Fast path에서 제거한 작업

  • 작은 수정에 requirement matrix나 WorkGraph를 만드는 일
  • 저장소 테스트가 있는데 같은 happy path를 별도 harness로 다시 만드는 일
  • 저장·인계 요청이 없는데 evidence JSON을 생성하는 일
  • 관련 suite 통과 뒤 근거 없이 검사를 계속 추가하는 일

외부 정답 접근과 무한 탐색을 막았다

  • workspace 밖 동일 프로젝트, package cache, gold/reference source를 구현 근거로 사용하지 않는다.
  • 복수 interface 작업만 편집 전 coverage census를 작성한다.
  • 두 diagnostic cycle 동안 새 증거가 없으면 탐색을 넓히지 않는다.
  • reference leakage가 발생하면 evaluator 성공과 관계없이 Not verifiable로 판정한다.

06 · Product direction

WIGTN Plugin 0.3.0의 방향

일반 구현·버그 수정 └─ Codex native workflow 또는 Fast path 제품 개발 계약이 필요한 작업 ├─ Product Spec 요구사항과 결정 ├─ Work Planner task, check, resume, drift ├─ Acceptance Verifier code·executed-test evidence └─ Release Readiness Git 상태와 실행 권한

0.3.0에 추가한 것

영역구현
Evidence Contract거짓 verified, 누락 gap, source drift, 권한 없는 외부 작업을 validator로 차단
WorkGraphrequirement→task→check 상태, 중단 재개, source hash 변경 시 stale 전파
Requirement importWIGTN Plugin PRD, Spec Kit, OpenSpec, BMAD 형식 정규화
Project context선택적 .wigtn/project.json으로 검증 명령과 보호 경로 공유
Screen contractIA·flow·screen·wireframe·handoff 연결과 requirement anchor 검사
Release statebranch, upstream, conflict, staged, unstaged, untracked를 mutation 없이 점검
Evidence inspection파일 변경과 hash drift 뒤 기존 완료 판정 재검사
평가 분리정적 계약, model behavior, 외부 benchmark를 별도 suite로 운영
Codex의 구현 능력은 그대로 사용하고, PRD에서 검증과 안전한 Git 릴리스까지 필요한 제품 개발 계약만 추가한다.

상태 파일은 일반 코딩 때 자동 생성되지 않는다. 저장형 계획, 세션 간 재개, 감사 가능한 handoff를 요청했을 때만 사용한다.

07 · Claim boundary

어디까지 믿을 수 있나

주장판정근거
정해진 PRD 계약의 재현성을 높인다제한적으로 지지GPT‑5.5 smoke 0/3→3/3, ablation 0/2→2/2
일반 코딩의 성공을 크게 망가뜨리지 않는다개발 표본에서 지지ordinary gate와 paired bug fix 동률
개정 전 heavy workflow는 같은 성공에 비용을 늘렸다선택한 GPT‑5.6 과제에서 지지4/4 tie, token·wall·command 증가
일반 코드 품질을 높인다지지되지 않음유효하고 재현된 positive lift 0
모델이 강할수록 항상 하네스를 줄여야 한다미검증두 모델과 작은 표본만 관측

한계

  • SWE-bench 주효과는 Python bug fix 두 과제, 네 pair다.
  • FeatureBench 파일럿은 네 과제이며 positive lift가 없다.
  • GPT‑5.5 실제 저장소 복제는 한 과제, 한 반복이다.
  • 독립 oracle 감사자와 blind human reviewer 수가 부족하다.
  • 프론트엔드, 데이터베이스, 대규모 migration 결과는 없다.
  • 0.3.0 개정 후 외부 holdout 반복은 아직 완료하지 않았다.

현재 가장 강한 결론: 선택한 GPT‑5.6 Sol bug fix에서 개정 전 WIGTN Plugin은 성공률을 바꾸지 않고 비용을 늘렸다. 이 결과를 반영해 일반 구현 절차를 줄이고 제품별 계약과 검증·릴리스 경계에 기능을 집중했다.
